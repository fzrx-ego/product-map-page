# The canvas — one pannable board over the storyboards

A second view over the same data as the scrolling storyboards: every screen of the product on
one board, transitions between them as arrows, comments as sticky notes beside them. The
scrolling pages stay — people search them with Ctrl+F, documents and tracker issues link to
them, they print. The canvas answers a different question: how the screens connect, and where
the holes are.

The toolchain lives in `assets/canvas/`. Copy it into the repository (a `scripts/` folder is
the usual place), point `canvas.config.json` at the project, and run it from there.

## What it produces

```
<map_dir>/storyboard/
  canvas.html            # shell plus the graph data
  canvas.bundle.js       # React + React Flow, built by esbuild as an IIFE
  canvas.bundle.css      # styling and the inlined font
  comments.json          # comments, edited by hand and committed
  assets-thumbs/         # frame previews, generated by the build
```

The page opens from disk with no network and no external resources — the same requirement the
scrolling storyboards are held to.

## Running it

```bash
npm install --prefix <scripts>/canvas-app     # once
python3 <scripts>/extract_routes_angular.py   # routes and transitions from the code
python3 <scripts>/link_storyboard.py          # attach storyboard frames
python3 <scripts>/build_canvas.py             # build the board
```

Refresh the frontend checkout first and check how old it is (`git -C <frontend> log -1`):
a graph built from a stale copy lies without saying so.

Everything project-specific sits in `canvas.config.json` next to the scripts:

```json
{
  "frontend": "../frontend",
  "storyboard": "docs/product-map/storyboard",
  "product": "Example",
  "title": "Example — screen canvas",
  "start_at": "/items",
  "groups": { "auth": "Sign in and sign up", "items": "Items", "settings": "Settings" }
}
```

`groups` maps the first URL segment to a board section; the key order is the order of sections.
A segment missing from the map lands in "Service screens" instead of being dropped. The scripts
find the repository root by walking up from themselves until they see the storyboard directory.

## The graph comes from code, not from prose

A transition is a directed edge with a cause: from where, to where, what triggers it. Neither
the prose of a storyboard nor a co-occurrence clustering will give you that. The only exact
source is the frontend code, where navigation is declared.

`extract_routes_angular.py` is the reference implementation. It reads:

| What | From |
|---|---|
| Route screens | `*-routing.module.ts`, and routes declared inline in `*.module.ts` |
| Sidebar menu | the nav data module; commented-out items are skipped |
| Card tabs | `tabItems` arrays in components |
| Row menu | `actionItems` arrays; `routerLink: 'id'` means opening the record |
| Buttons and links | `routerLink` in templates: absolute, relative, `new` |
| Row click | `<tr [routerLink]="…['id']">` → the child route carrying a parameter |
| Back button | the route's `data.backUrl` |
| Code navigation | `router.navigate`, `navigateByUrl` |

Labels of buttons and tabs are resolved from string enums and from the i18n file, so the graph
carries the text the user sees rather than a translation key.

**Everything the extractor cannot read must land in `unresolved.md`.** An empty file means
everything was read. Dropping a transition silently is not acceptable: a missing edge looks
exactly like "this screen is unreachable", which is indistinguishable from a real finding.

Another stack needs its own extractor. What it must emit:

```json
{
  "generated": "2026-08-22",
  "source": { "repo": "../frontend", "commit": "d5e29b4 2026-08-13" },
  "nodes": [
    { "url": "/items", "title": "Items", "kind": "screen", "component": "ItemsComponent",
      "roles": ["Admin"], "guards": ["AuthGuard"], "redirect_to": null, "back_url": null,
      "tab": null, "source": "src/app/pages/items/items-routing.module.ts" }
  ],
  "edges": [
    { "from": "/items", "to": "/items/:id", "trigger": "click on a list row",
      "kind": "row-click", "evidence": "src/app/pages/items/items.component.html:74" }
  ]
}
```

`kind` on an edge is free-form but groups into four buckets for the filters: navigation, tabs,
states, back. `from: "*"` means "from any screen" — the sidebar, the header, forced redirects.

## Two layers of nodes

1. **Routes** — from the code: address, component, roles, guards, redirects.
2. **States inside a screen** — from the frame captions (`visual-cap`) in the storyboards:
   modes, tabs, empty states, wizard steps. `link_storyboard.py` splits a caption like
   `Desktop · /items/:id/settings · Advanced`: the part with an address is the route,
   the rest is the state.

Hence the rule for storyboards: **a frame caption always carries the address**. Without it the
attachment rests on a hand-written table in `states-manual.json` and breaks the first time the
screen is re-captured.

## Keep the hand-written files small

| File | What is in it |
|---|---|
| `edges-manual.json` | transitions that cannot be read from code; each records `why_manual` |
| `states-manual.json` | state nesting that is in neither the code nor the caption |
| `comments.json` | team comments and the extractor's findings |

If the same case shows up twice, that is a rule for the script, not another line in a
hand-written file.

## Comments

They live in `<map_dir>/storyboard/comments.json`, are edited by hand, committed, visible to
everyone and part of the history. There is no live "leave a note on the board" — for working
notes about screens this is enough, and the board stays an artefact of the repository rather
than of an external service.

```json
{
  "comments": {
    "/items": [
      { "kind": "note", "author": "Ann", "date": "2026-08-22", "text": "…" }
    ],
    "/items/:id/settings#settings-advanced": [ … ]
  }
}
```

The key is a node address: a route, or a state as `<route>#<frame anchor>`. `kind` is `note`
(written by a person) or `finding` (produced by the reconciliation scripts); they differ in
sticky colour. Re-run `build_canvas.py` after editing.

## Layout and frames

Python computes the layout. There is deliberately no auto-layout: the order of screens on the
board must follow the user's path, not the convenience of an algorithm. Screens are grouped
into frames by section, and inside a frame they run left to right by depth: list → record →
tabs → modes. Cards are not draggable — positions are recomputed on every build.

- Screen card 640 px, state card 560 px; height follows the frame's real proportions.
- Long forms are cropped from the top (900 px for a screen, 620 for a state) and marked
  "frame cropped": what differs between such frames sits in the upper part, and showing them
  whole inflates the board fourfold.
- Frames come in two sizes: a 680 px preview for the overview, swapped for the full frame from
  zoom 0.9 on visible cards. Otherwise the board is either unreadable up close or holds every
  full-size frame in memory at once.
- A screen with no frame of its own shows the frame of its first state and says so, on the card
  and in the panel.
- Sticky height is computed by `sticky_height()` from the text length; the width is tied to
  `STICKY_CPL` — change one, recompute the other.

The board opens on the screen named by `start_at`, not on the overview: at overview zoom the
frames are physically unreadable no matter how large the cards are.

## Panels

Bottom left, a dock of icons (transition types, groups, search). Bottom right, a vertical zoom
dock (+, an editable percentage, −, fit, 1:1, minimap). On the right, the explanation panel
slides in. Long lists take no room in the dock: transition types and groups open as popovers,
search expands into a field across the dock's width and collapses on the cross. Zoom shortcuts
are `+`, `−`, `⇧1`.

## Traps already stepped in

- **The bundle must be an IIFE.** `file://` forbids module scripts: an ES module yields a blank
  page with nothing in the console.
- **`setPointerCapture` breaks clicks.** Capture retargets later events to the pane, so
  `ev.target.closest('.card')` returns null on release. Record the card under the cursor on
  press instead.
- **Class names collide.** A `.find` class on the search panel overrode the `finding` sticky
  modifier and squashed it to the panel's height. Keep node classes and panel classes in
  separate prefixes.
- **A fixed sticky height cuts text** mid-word. Compute it from the length.
- **Caption inheritance between frames.** A frame with no caption inherited the previous
  address and overwrote another screen's frame. Inherit only when a caption exists but carries
  no address.
- **Check with your eyes, not only for absence of errors.** Clicking a card did not work at all
  while the console stayed clean. A Playwright pass with screenshots and clicks is mandatory.
